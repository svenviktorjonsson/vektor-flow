# Large-scene visualization comparison

## Current status

This directory contains the versioned workload contract, deterministic fixture
generator, report validator, and release ratchet. It contains **no measured peer
results**. `results/scaffold.json` is deliberately marked `scaffold`; running it
prints `no performance claim`.

The internal VKF adapter and a correctness-only headless WebGL capture now exist.
Equivalent deck.gl, VTK.js, and Plotly adapters are still required before a row
can change from `scaffold` to `published`. Browser work must run headless, or in
the repository's explicitly hidden/off-screen hardware mode. A visible browser
is not permitted for this suite.

## Why these peers

- [deck.gl](https://deck.gl/docs/developer-guide/performance) is a direct
  large-data WebGL/WebGPU visualization peer. Its official guidance discusses
  million-item `ScatterplotLayer` scenes, binary inputs, update cost, and
  overdraw. The lane uses the documented
  [ScatterplotLayer](https://deck.gl/docs/api-reference/layers/scatterplot-layer).
- [VTK.js](https://github.com/Kitware/vtk-js) is the web member of a mature
  scientific-visualization toolkit. Its
  [Mapper](https://kitware.github.io/vtk-js/api/Rendering_Core_Mapper.html)
  exposes static-data behavior and last-render time, while the
  [SphereMapper](https://kitware.github.io/vtk-js/api/Rendering_Core_SphereMapper.html)
  supplies a GPU point-glyph lane whose orthographic silhouette can match the
  fixed circular marker contract.
- [Plotly.js scattergl](https://plotly.com/javascript/reference/scattergl/) is a
  widely used high-level plotting peer. Plotly's official
  [WebGL examples](https://plotly.com/javascript/webgl-vs-svg/) explicitly cover
  100,000 and one million point marker plots.

The versions in `manifest.json` were resolved from their official npm packages
on 2026-08-31 and must be installed into a lockfile by a future adapter packet.
They are research pins, not evidence that those packages were executed here.

[regl](https://github.com/regl-project/regl) was considered but is not a
published peer in this contract: it is a low-level WebGL command library, so a
comparison would mostly benchmark a new benchmark-specific renderer. luma.gl is
not a separate row because it is already the rendering foundation beneath the
selected deck.gl lane.

## Equivalent workloads

| Workload | Data | Per-frame responsibility |
| --- | ---: | --- |
| `orthographic-points-100k-static` | 100,000 packed `x,y` float32 points | fixed camera; render only |
| `orthographic-points-1m-pan` | 1,000,000 packed `x,y` float32 points | update the same camera-only sinusoidal pan |

Both use 1280×720 physical pixels, device-pixel ratio 1, a two-pixel circular
marker, the same color/background, fixed orthographic bounds, disabled picking,
and no axes, map, labels, or hover UI. The generated bytes and their SHA-256
hashes are identical across implementations. Position buffers are uploaded
during preparation and remain unchanged during measured frames. An adapter that
rebuilds or reuploads point data during the one-million-point pan is not
comparable and cannot publish a row.

The VKF adapter uploads the exact packed `x,y` fixture once through a private
retained-data marker. Its later pan frames change projection uniforms and redraw
without reallocating, rewriting, or changing the WebGL point buffer. Ordinary
renderer calls keep their previous mutable-buffer behavior and still upload when
called again; no public VKF API changed. Until every peer adapter exists, all
lanes remain scaffolds.

## Correctness before timing

Every publishable lane must first render every declared camera checkpoint and
read back its framebuffer. The camera formula is manifest data: the pan uses
`phase = 2*pi*frame/frames` and the same sine/cosine offsets in every lane.
`sampled-frame-regions-v1` partitions the image into the manifest's 16×9 grid.
Its `ideal-disc-source-over-v1` reference maps each `x,y` through the declared
orthographic range, rasterizes the two-pixel disc with an 8×8 fixed subpixel
grid, source-over composites in fixture order, and calculates foreground
coverage plus premultiplied RGBA means for each region. The maximum normalized
component error must stay at or below the predeclared limit. A report records the
captured artifact SHA-256, dataset SHA-256, workload-contract SHA-256, error, and
the sequence proving correctness completed before timing began.

A Boolean without those hashes, error bounds, and ordering is rejected. The
oracle intentionally uses region statistics rather than whole-image equality so
documented subpixel raster differences cannot hide missing data, a wrong camera,
wrong color, or wrong marker coverage.

## Measurement and ratchet

Preparation/upload time is reported separately. The release ratio uses median
`steady-frame-ms` over at least 120 measured frames after at least 60 warmup
frames. Each frame covers the same camera update through explicit GPU completion
(`gl.finish` for WebGL or `queue.onSubmittedWorkDone` for WebGPU). Implementation
order rotates between repeats. All rows in one report share the exact host, GPU,
browser, viewport, power mode, manifest, dataset, and timing boundary.

For every published workload/peer row:

```text
ratio = VKF median steady-frame-ms / peer median steady-frame-ms
0.4.0 requires ratio < 1.5
```

Equality fails, and there is no aggregate score that can hide a slow row. The
future `ratio < 0.5` goal is recorded as `deferred` for 0.6.0 and is not enforced
by the 0.4.0 validator.

## Run the scaffold gate

```powershell
npm run test:large-scene-benchmark-harness
node benchmarks/large-scene-visualization/run.mjs
npm run capture:retained-point-camera
```

The second command validates generated fixture hashes and the checked-in
unmeasured report. It must say that there are zero published comparisons. The
capture command uses `--headless=new` plus SwiftShader strictly as a correctness
oracle: it proves one eight-megabyte million-point upload, changed pixels after
camera pan, and bounded region error. It records no timing and sets
`performanceClaim: false`. A future measurement command passes an evidence
report explicitly:

```powershell
node benchmarks/large-scene-visualization/run.mjs --report=path/to/measured-report.json
```

No table or release note may call a scaffold or a correctness failure a baseline.
